FITNESS RPG — CLAUDE PROJECT PLAN
=================================

Document purpose
----------------
This document is the implementation brief for building a mobile fitness RPG with Claude. It should be kept in the project root and treated as the product and engineering source of truth. Build the application in controlled phases. Do not attempt to generate the entire product in one pass.

Core implementation rule:

Fitness functionality comes first. RPG elements should make training more motivating, but they must never slow down or interfere with logging a workout.

The product should take inspiration from progression-fantasy concepts such as players, awakening, levels, ranks, quests, gates, classes, bosses, XP, and attributes, while using an original name, visual identity, story, artwork, terminology, and copy. Do not copy protected characters, logos, artwork, dialogue, or recognizable screen designs from Solo Leveling or any other property.


1. PRODUCT VISION
=================

Working concept:

“A fitness RPG where your real-world training determines your character progression.”

The app is a serious workout tracker underneath and an RPG progression system on top. The core loop is:

Quest -> Workout -> XP -> Level Up -> Attribute Growth -> Rank Up -> Harder Gates

The product combines:

- Fast, reliable workout logging
- Workout templates presented as “Gates”
- Exercise strength rankings
- Per-workout Gate Clear rankings
- Body-composition assessments
- Player levels and XP
- Hunter ranks from E through S
- Automatically calculated fitness attributes
- Daily and weekly quests
- Personal-record detection
- Progress analytics
- Workout streaks and adherence
- Later: classes, cosmetic inventory, boss challenges, friends, guilds, and raids

The dashboard must answer four questions immediately:

1. Who am I?
2. How strong or fit am I?
3. What should I do today?
4. How close am I to my next milestone?

Product hierarchy:

Hunter Rank
  -> Strength, Physique, Endurance, Discipline
  -> Exercise Ranks and assessment data
  -> Gates and workout performance
  -> Gate Clear Rank

Cadence rule:

- Hunter Rank changes slowly.
- Exercise Ranks change occasionally.
- Gate Clear Rank changes every workout.

This gives the user an achievable victory in every session without making long-term ranks meaningless.

Architecture rules

- Screens compose features and reusable components; they do not own domain formulas.
- rankingEngine.ts contains pure ranking functions.
- Progression and XP calculations must be pure, deterministic, and testable.
- Database access goes through typed service/repository functions.
- TanStack Query owns server state. Zustand must not duplicate the remote database cache.
- Theme values come from tokens, never scattered hard-coded colors.
- All measurements support metric first, with unit conversion designed for future imperial support.
- Store canonical weight values in kilograms.
- Handle loading, empty, offline, and error states explicitly.
- Never trust client-supplied ownership fields; enforce ownership with database policies.

6. RANKING AND PROGRESSION SYSTEMS
==================================

6.1 Shared rank thresholds

- 0-19: E
- 20-34: D
- 35-49: C
- 50-64: B
- 65-79: A
- 80-100: S

Keep thresholds in configuration constants so they can be tuned without changing UI code.

6.2 Estimated 1RM

For conventional strength exercises, begin with the Epley estimate:

estimated1RM = weight * (1 + reps / 30)

Use only qualifying working sets in the 1-12 rep range for strength ranking. Warm-up sets, incomplete sets, invalid data, and implausible values must not affect rankings. Bodyweight and assisted exercises need their own strategy and should not silently use an inappropriate barbell formula.

6.3 Permanent Exercise Rank

Purpose: historical capability on a specific exercise.

Inputs may include:

- Best valid estimated 1RM
- Bodyweight-relative strength
- Sex and age where evidence-based normalization data is available
- Exercise type
- Performance percentile or validated reference table

Target pipeline:

Performance data -> Percentile/reference comparison -> Normalized score 0-100 -> Exercise Rank

Do not invent authoritative population standards. Start with clearly labeled provisional thresholds or seed data, isolate them in configuration, and document how they will be calibrated.

6.4 Workout Performance Grade

Purpose: how the user performed today relative to their expected recent performance.

This is separate from Permanent Exercise Rank.

Example:

- Permanent: Bench Press — B Rank
- Today: Bench Press Performance — A Grade

Use separate names in code: exerciseRank and performanceGrade.

6.5 Gate Difficulty and Gate Clear Rank

Gate Difficulty is assigned before training and represents the intended workout challenge.

Gate Clear Rank is calculated after training and represents actual session quality.

Never use these terms interchangeably.

Initial Gate Score weights:

- Exercise performance: 50%
- Completion: 20%
- Progress versus prior sessions: 15%
- PRs: 10%
- Training quality/RPE validity: 5%

Example:

gateScore =
  performance * 0.50
  + completion * 0.20
  + progress * 0.15
  + prScore * 0.10
  + quality * 0.05

Clamp every input and final result to 0-100. Define behavior for first-time workouts with no history. Do not punish new users for missing comparison data; renormalize available factors or use a documented neutral baseline.

6.6 Rank validation and anti-inflation rules

- Do not rank a user from one implausible set.
- Require at least two valid working sets for a qualifying performance.
- Reject impossible or clearly erroneous weights, reps, RPE, and time values.
- Require major rank upgrades, especially A to S, to be demonstrated in at least two separate sessions.
- Compare against recent history and flag abnormal jumps rather than automatically accepting them for rank progression.
- Preserve raw logs even when a set is excluded from ranking, unless the user deletes it.
- Explain why a performance did or did not qualify.

6.7 Hunter Rank

Hunter Rank combines long-term attributes:

- Strength: 40%
- Physique: 30%
- Endurance: 15%
- Discipline: 15%

hunterScore =
  strength * 0.40
  + physique * 0.30
  + endurance * 0.15
  + discipline * 0.15

Map the resulting 0-100 score to E-S. Keep the formula configurable and show users which attribute is limiting the next rank.

6.8 Physique score

Do not copy or rely only on the InBody score. A future physique model may use:

- Muscle development: 40%
- Healthy body composition: 30%
- Muscle/segmental balance: 20%
- Lean mass relative to height: 10%

Do not reward endlessly lower body-fat percentages. Use healthy, non-punitive ranges. Treat physique results as estimates, avoid medical claims, and provide appropriate privacy and wellness language.

6.9 Discipline score

Calculate from:

- Planned workouts completed
- Training consistency
- Current and long-term streak behavior
- Long-term adherence

Do not encourage unsafe “never miss a day” behavior. Scheduled rest days must not break a streak. Allow recovery, illness, and plan changes to be handled fairly.

6.10 XP and levels

Rank is not Level.

- Rank represents demonstrated performance.
- Level represents activity and account progression.

Initial XP examples:

- Complete a workout: +300 XP
- Complete a valid working set: +10 XP
- Earn a meaningful PR: +50 XP
- Complete a daily quest: +100 XP
- Complete a weekly quest: +500 XP
- Gate clear bonus: +100 to +300 XP

Do not award XP for every button press. Prevent duplicate rewards and repeated claim exploits.

Initial level curve:

xpRequiredForLevel = 100 * level^1.5

Implement this as getXpRequiredForLevel(level), with economy constants outside the UI.
